## When to use

- **Exactly one answer, from a set that is short enough to show.** Every option
  is on the page at once, so the reader compares them without opening anything.
  Past roughly seven options the set stops being scannable and belongs in
  `Select`.
- **When the options are worth reading.** A radio group spends vertical space to
  make the alternatives visible; if the reader already knows what they want and
  the list is long, that space is wasted.
- **Not for on/off.** One radio on its own cannot be unchecked once chosen, so a
  single yes/no is a `Switch` or a `Checkbox`.

</div>

<div className="sb-ds-doc-section">

## Usage notes

- **`Radio` is one option, not the group.** The group is whatever shares a
  `name`. Nothing here renders the set, names it or manages which member is
  chosen — `MultipleChoice`, `RadioButtonGroup` and `ChoiceGrid` do that.
- **`checked` makes it controlled and `defaultChecked` is then ignored.** Pass
  `checked` with an `onChange` that sets it, or pass `defaultChecked` and let
  the browser hold the state. Passing both is the mistake that renders a radio
  which cannot be selected.
- **`size` changes the control as well as the label.** The dot is 10px on
  `small`, 12px on `medium` and 14px on `large`, and the label takes
  `body3-txt`, `body2-txt` and `body1-txt` to match. All three dots are well
  under a 24px target, so the hit area comes from the label — which is why a
  radio without a `label` is a hard thing to point at as well as an unnamed one.
- **Extra props land on the input.** `aria-label`, `required`, `data-*` and the
  rest are spread onto the control rather than the wrapper, so they reach the
  thing that has the role.

</div>

<div className="sb-ds-doc-section">

## Accessibility

- **The label is wired for you, `id` or no `id`.** One id is derived through
  `useFieldId` and handed to the underlying form check, which renders the
  `label` with a matching `htmlFor`. Pass `id` when something outside the
  component needs to point at the input — an `aria-describedby`, a test
  selector — and you get exactly the id you passed.
- **A group's shared `name` cannot double as its ids (#222).** The id used to
  fall back to `name`, and radios in a group share a `name` — that is what makes
  them one group. So a group written without `id`s gave every option the same
  id, and every label in it resolved to whichever radio the browser reached
  first. Each radio now derives its own id, so the group is wired correctly with
  no `id`s at all.
- **A radio with no `label` has no accessible name.** Nothing substitutes for it.
  Where the design has no room for visible text, pass `aria-label`; it is spread
  onto the input.
- **Nothing here names the set.** `name` groups the radios for the form, not for
  a screen reader. Wrap related radios in a `fieldset` with a `legend`, or hand
  the whole set to `MultipleChoice` or `Scale` — see
  `design-system/guidelines/foundations/accessibility.md`.

</div>

## Related

- For one answer from options held in an array, use `MultipleChoice` with `type="radio"`.
- For the same single choice drawn as a segmented control, use `RadioButtonGroup`.
- For any number of answers rather than exactly one, use `Checkbox`.
- For choices in a popup rather than on the page, use `Select`.
- For a rows-by-columns matrix of choices, use `ChoiceGrid`.
