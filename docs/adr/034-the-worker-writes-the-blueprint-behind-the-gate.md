# ADR-034: The Worker writes the blueprint behind the gate (2026-10-15)

**Decision.** The Worker becomes a gated blueprint writer, reversing "write access: `writers/blueprint` only". A **blueprint revision** — the drafted cell changes to one path, each with its status before and after, plus an optional path status — is staged as one card whose single operation is the `worker` tool `blueprint_revise` (`agents/uno-bot/src/blueprint-write/`). Its confirmers are exactly the people the card names, the standing confirmers left out (`exclusiveConfirmers`, a new card term every other card leaves unset). On a ✅ from one of them, the Worker signs in as its own Auth user, `app_metadata.role = rpc_writer` (`SUPABASE_WRITE_EMAIL` in `[vars]`, the secret `SUPABASE_WRITE_PASSWORD`), and writes every row through `upsert_cell_at_status` and the path through `set_path_status`. A proposal drawn from a conversation is a revision with a `variant`: the Worker first creates a new `proposed` `variant` path beside the matched one through `create_path_at_status` (lanes and step order copied from it), then writes the idea's cells there, so today's cells are never written. ⛔, expiry and a lost race reach no RPC. `writers/blueprint` stays the IDE writer through the Supabase MCP; the Worker's writer is the second, narrower one.

**uno-bot is its own author.** `authoring_changes.author` gains a third value, `uno-bot`, beside `human` and `agent` (Bill, 2026-10-15). A database trigger stamps it, with `author_id` uno-bot's account, on every row appended under the `rpc_writer` JWT, whichever function appends it, and refuses the value from anyone else. A `uno-bot` row carries the approval's agent session when the call passed one; a delete function's row carries none. Two kinds of RPC put the row there:

- **Self-recording:** `upsert_cell_at_status`, `set_path_status`, `create_path_at_status` and the delete functions append their own row in the same transaction.
- **Caller-recorded:** every older RPC (`add_step`, `create_path`, …). The Worker follows each with `record_authoring_change` under the approval's session, as the canvas does (`authoringCall`).

Only the status-aware RPCs create a row at `proposed` or `planned`: no older RPC writes `status`, and `upsert_cell` and `create_path` insert at `live`.

**uno-bot may delete.** It calls the delete RPCs as a human service account does (Bill, 2026-10-15), reversing "deletes are human-only" for the Worker. Each delete is recorded and archived by the function itself, and lands in the log as `uno-bot`.

**All or none.** A revision is reviewed whole, so it is written whole. A failed write, or a cell that moved since the draft (a slot filled, a status changed — a stale race), takes back every write already made, that one included, newest first. A changed cell is put back as it stood through `upsert_cell_at_status`. A cell the revision created is deleted through `delete_cell`. What could not be taken back is named in the thread. Removing a drawn proposal is still a status write to `deprecated`.

**Budget (ADR-022).** A self-recording call is one subrequest; a caller-recorded call is two, the RPC and its record (`authoringCallCost`). Sign-in is one more, at most once an hour per isolate. Before its first call the tool takes the revision's worst case — every write and every take-back at that cost, plus sign-in — and refuses the press, writing nothing, when that and a four-call reserve for the thread's reply exceed the headroom. A job that drafts revisions keeps each one within that ceiling.

**Why.** Shipped work changes the service, and a revision someone has to carry to the IDE afterwards is the drift the blueprint already suffers. The Worker has the draft and the approval in hand, so it writes. The narrowness is the point: the RPC guards admit `rpc_writer` only inside a SECURITY DEFINER body, so the identity reaches the blueprint through recorded operations and no table, and the service-role key stays off the Worker (plus-uno-blueprint `20261015120000`). Deleting through the same recorded RPCs a person uses is what lets a take-back leave the blueprint as it found it, instead of a `deprecated` cell a person has to clean up. A distinct author keeps the bot's writes separable from a person's in the log, and stamping it in the database means no caller can forget it or claim it. Owner-or-Bill confirmers, not the standing list: product truth changes only with the person who shipped it or the person who makes product calls (#1279).

**Consequences.** Every Worker write is traceable to uno-bot in `authoring_changes`, and to its approval by the agent session wherever the call could carry one. A caller-recorded write can land unrecorded if its record call fails, so the writer keeps to the self-recording RPCs where one exists. The setup lives in the uno-blueprint deployment, not the template. The connector doc's access table names the Worker's writer. Rollback: drop the tool row and redeploy; the identity's password can be rotated or the Auth user disabled in the dashboard without a deploy. — uno (agent), Oct 2026, applying #1285
