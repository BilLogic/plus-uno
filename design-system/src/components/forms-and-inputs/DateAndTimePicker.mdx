## When to use

- **When a moment needs both halves.** A session start is a date *and* a time,
  and splitting it across two fields makes the reader hold the pair together
  themselves. Where only one half matters, use `DatePicker`.
- **`showDate={false}` gives a time-only control** without reaching for a
  different component, which keeps the time half's parsing and its AM/PM
  behaviour rather than reimplementing them beside it.
- **Not for a duration.** This picks a point, not a length. Two of these, or a
  `NumberInput` of minutes, says what a single one cannot.

</div>

<div className="sb-ds-doc-section">

## Usage notes

- **`onChange` does not hand you an event.** It is called with
  `{ date, time, utc }` — plain strings, or `null` for a half that is not yet
  complete. `utc` is the moment as ISO 8601 in UTC, worked out in `timeZone`;
  store that, not `date` and `time`, which are only what the viewer saw. Every other field in this group forwards a DOM event, so this is
  the one place `event.target.value` will be undefined.
- **`time` stays `null` until both hours and minutes are present.** A reader
  part-way through typing produces `{ date: '03/14/26', time: null }`, which is
  the honest report: `09:` is not a time.
- **The hour shown is a 12-hour hour.** `timeValue` accepts either form —
  `"02:30 PM"` is used as given, and `"14:30"` is split into `02:30` and `PM`.
  Midnight and noon are the two that do not follow the modulo and both read as
  `12`, with only the period telling them apart.
- **The hour field refuses what the control cannot show.** It takes 0 to 12, not
  0 to 23, because an AM/PM control sits beside it. Zero is inside the bound so
  a leading zero can be typed on the way to `05`.
- **Changing AM/PM reports, with or without a date.** The event carries
  `date: null` when no date has been picked yet, rather than staying silent
  about a change the reader can see.
- **Times are stored in UTC and shown in the viewer's zone.** `timeZone` is the
  viewer's IANA zone and defaults to the browser's. The caption under the time
  names it — "Eastern Time (ET)" — unless `showTimeZone={false}`. Pass
  `otherTimeZone` and `otherPerson` when someone else will read the time, and
  the caption adds theirs: "Pacific Time (PT) · 4:00 PM for the student (ET)".
  Daylight saving is handled per date, so a 4:00 PM in November is an hour later
  in UTC than one in October.
- **The calendar opens 4px below the date field.** It is the same calendar as
  `DatePicker`, `--size-element-gap-xs` below, left-aligned, flipping above when
  there is no room. The AM/PM menu opens the same 4px below its button.
- **Extra props go to the wrapper, not to the two inputs (#230).** The wrapper
  is the element that carries the group's role and name, so a caller's
  `aria-describedby` lands where it can help. They go on last, so a caller's
  `aria-labelledby` overrides the generated one.

</div>

## Accessibility

- **`label` names the field, not either input.** The field renders two controls,
  and one `<label for>` names one control, so `label` labels a `role="group"`
  around both (#206). Each input is then named off that plus its section
  heading — `<field> Date` and `<field> Time` — which is what tells them apart
  once they are read out of context.
- **`showLabel={false}` hides the label, it does not remove it.** The label is
  rendered either way and always carries `htmlFor`; `showLabel={false}` only
  clips it out of sight with `.plus-datetime-label-hidden`, so the group and
  both inputs keep their names and the layout does not move. This was the other
  way round until #225, which brought the component in line with `Input`
  (#213) — see *Why `showLabel` cannot take the name away* in the Input docs.
- **A field with no `label` still has no name.** `showLabel` decides whether the
  label is *seen*; passing no `label` is what leaves the field unnamed. Then
  there is no group either, and the two inputs are called just "Date" and
  "Time" — off their section headings, or off a fallback `aria-label` when
  `showSectionLabels` is off. Both are true of the control and useless as a
  field name: two such pickers on one screen are indistinguishable.
- **A caption you render above the field cannot be its name.** The pattern that
  prompted #225 — one visible "Session time" over a start and an end picker —
  has no `htmlFor` that works, because one `<label for>` reaches one control and
  there are two fields under it. Give each picker its own `label` with
  `showLabel={false}`, and let the caption name the pair: put it in an element
  with an `id` and point a wrapping `role="group"` at it with
  `aria-labelledby`. `Specs/Toolkit/Pre-Session/Elements/New Form Time Input` is
  the worked example, and its `play` block is the regression cover.
- **Never hand the same `id` to two pickers.** Ids are derived once per instance
  (`useFieldId`), so omitting `id` is safe and unique. Repeating one is not: both
  fields' labels and `aria-labelledby` targets then collide, and every label on
  the page lands on whichever control the browser reached first (#222).
- **`validation` marks both inputs.** Both halves are `_Field`, so
  `validation="invalid"` draws both boxes in the error state and sets
  `aria-invalid` on both inputs, and the message is the shared field caption,
  announced as an alert, which describes the group. `required` renders a `*`
  span marked `aria-label="required"`. Until #230 a caller had no escape hatch
  either — this component collected the props it does not name into a rest
  object and never spread it, so passing `aria-describedby` yourself did
  nothing, silently. It forwards them now; the rule for where they land is the
  next bullet.
- **Forwarded props go to the wrapper, which is the group — not to either
  input.** Anything this component does not name in its own signature is spread
  onto the outer `<div>`, the same element that carries `role="group"` and the
  field's name (#230). One target, because this field renders two inputs plus an
  AM/PM control and a prop split across them would land somewhere the caller did
  not choose. The wrapper is the right one of the four: it is what `data-testid`
  means by "this field", and it is what `aria-describedby` is about — a
  description of the field describes the field, not its date half. The spread is
  last, so a caller's `aria-labelledby` wins over the generated one, matching
  `Input`. One dependency worth knowing: the wrapper is only a `group` when the
  field has a `label`, per the third bullet above, so a description forwarded to
  an unlabelled picker lands on a plain `<div>` and is announced by nothing.
  Pass a `label` — with `showLabel={false}` if it should not be seen.
- **What that rule costs you: a forwarded `aria-invalid` marks the group, not
  the inputs.** It is the honest consequence of one spread target, and the
  reason to use `validation` instead, which marks the inputs themselves.
- **The time-zone caption is part of the description.** It is linked through
  `aria-describedby` after any description you pass, so a reader hears the zone
  along with the field.
