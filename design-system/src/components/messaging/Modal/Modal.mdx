## When to use

Use `Modal` when the next step has to happen before anything else can — a
destructive confirmation, a short form that would derail the page, a detail view
that the user will close and return from. It is the only messaging component
that takes focus away from the page, so use it when interrupting is the point.

The footer is built in: pass `primaryButton` and `secondaryButton` as objects and
the component renders the `Button` pair for you, aligned right. Pass `footer` for
other actions, such as a Delete on the left or a single primary.

Pick a grid `width` for the content rather than a number: `sm` for a confirm, `md` for a
short form, `lg` for a table or an editor. A dialog never opens another dialog.
When a follow-up decision comes up inside one — confirming a delete, for
example — swap its content for an inline confirmation in the same dialog
rather than opening a second one. Opening a modal closes a floating sidebar; a
docked one stays.

</div>

## Usage notes

### Size the modal by the grid, not by a number.

```jsx
// Incorrect — a fixed width ignores the screen grid, so the dialog keeps one
// size on every screen. Numbers are kept only for the callers that still pass one.
<Modal width={480} title="Reschedule" show={open} onClose={close} />

// Correct — a width from the screen grid, which grows with the screen.
<Modal width="md" title="Reschedule" show={open} onClose={close} />
```

### The footer only appears when you give it a button.

```jsx
// Incorrect — `showBottomButtons` defaults to true, but with neither button
// nor `footer` supplied the footer is not rendered at all, so the dialog ends
// with no way to confirm.
<Modal title="Reschedule" show={open} onClose={close}>{form}</Modal>

// Correct — describe the actions; the component renders the Button pair.
<Modal
  title="Reschedule"
  show={open}
  onClose={close}
  secondaryButton={{ text: 'Cancel', onClick: close }}
  primaryButton={{ text: 'Reschedule', onClick: submit }}
>
  {form}
</Modal>
```

### Inline confirmation

A follow-up decision — confirming a delete, for example — replaces the
dialog's title, body and footer in place. It does not open a second dialog.

### Confirm a follow-up decision in place, not in a new dialog.

```jsx
// Incorrect — a second Modal opens on top of the first. Dialogs never stack.
<Modal title="Session settings" show={open} onClose={close}>
  {settingsForm}
  <Modal
    title="Discard changes?"
    show={confirmOpen}
    onClose={closeConfirm}
    secondaryButton={{ text: 'Back', onClick: closeConfirm }}
    primaryButton={{ text: 'Discard changes', appearance: 'danger', onClick: discard }}
  >
    Your edits to this session are not saved.
  </Modal>
</Modal>

// Correct — the same dialog swaps its title, body and footer for the
// confirmation, and Back returns to the form without losing what was typed.
<Modal
  title={confirming ? 'Discard changes?' : 'Session settings'}
  show={open}
  onClose={close}
  secondaryButton={
    confirming
      ? { text: 'Back', onClick: () => setConfirming(false) }
      : { text: 'Cancel', onClick: close }
  }
  primaryButton={
    confirming
      ? { text: 'Discard changes', appearance: 'danger', onClick: discard }
      : { text: 'Save', onClick: save }
  }
>
  {confirming ? 'Your edits to this session are not saved.' : settingsForm}
</Modal>
```

## Accessibility

- **Escape and backdrop click are on by default.** `keyboard` and `backdrop`
  both default to `true`. Turning either off leaves the header close button as
  the only exit, so keep that button — it is only rendered when the modal is not
  in body-only mode (`title` absent *and* `showBottomButtons` false).
- **The close button is labeled `Close modal`**, hard-coded. Its icon is
  `aria-hidden`. `showCloseButton={false}` removes it; keep Escape or a footer
  action as a way out.
- **The title is the dialog's h1 and its accessible name**, through
  `aria-labelledby`: the dialog reads as its own page. The `description`
  describes it, through `aria-describedby`. A modal with no title takes
  `ariaLabel`.
- **A body that scrolls is focusable.** Once the content runs past the cap, the
  body gets `tabIndex={0}` so a keyboard user can scroll it — the axe
  `scrollable-region-focusable` rule. `type="scrollable"` sets it always.
- **Loading is announced as busy.** `loading` sets `aria-busy` on the body while
  the skeleton bars stand in for it.
- **Opening traps focus inside the dialog and closing returns it to the
  trigger.** Tab cycles within the dialog rather than escaping it; a view
  change (the confirm view swapping in) moves focus into the dialog again,
  since the control that raised it is gone from the footer.
- **Dismiss is Close, Escape, a Blanket click, or an optional Cancel.** An
  inline confirmation of a destructive action turns off the Blanket click, so a
  stray click outside the dialog cannot destroy something by accident — Close,
  Escape or the footer's Back still work.
- **Focus order is Close, then the content, then the secondary action, then
  the primary action.** Tab follows that order on open, and focus returns to
  the trigger on close.

### Do not use the inline render for a live dialog.

```jsx
// Incorrect — no backdrop, no focus trap, no Escape. The page behind stays
// fully interactive and keyboard users can tab straight past the dialog.
<Modal renderAs="inline" title="Delete session" show={open} onClose={close} />

// Correct — the default `renderAs="modal"` wraps the content in the real
// dialog, which handles the backdrop, focus and Escape.
<Modal title="Delete session" show={open} onClose={close} />
```

## Related

- For a message the user only has to read, use `SectionMessage` or `Flag`.
- For long content, use a page rather than a dialog — a modal traps focus, and scrolling inside one is hard to navigate.
- For a menu or a picker, use `Dropdown` or `Select`.
