<FoundationSection title="Overview">

Tokens are how the tutor and student apps apply color, type, spacing, radius, borders and elevation. A token has a name that says how to use it and a value that can change by theme, so one choice is made once and every screen follows.

<Banner appearance="announcement">
<strong>Two name notations</strong><br />
PLUS writes a token with slashes in Figma (`color/text/subtle`) and as `--ds-text-subtle` in code. To start by task: use tokens in code (Using tokens in code), or choose a token in design (Choose a layer).
</Banner>

Code reads `--ds-*` for color and elevation, `--pad-*`, `--stack-*`, `--inline-*` and the other semantic prefixes for shared steps, `--card-*`, `--table-*`, `--modal-*` and the other pattern prefixes for patterns, and `--space-*`, `--radius-*` for primitives. Figma reads local variables grouped into the collections below.

</FoundationSection>

<FoundationSection title="Non-negotiable rules">

- Color, spacing, typography, radius and elevation come from compile-ready tokens, such as `var(--ds-text)`: never raw values, and never Figma literal names.
- Never hardcode a color, spacing, typography, radius or elevation value when a token exists.
- Choose the tier first (component, then pattern, then semantics, then primitives; see The four-tier ladder), then pick the token.
- Use primitives only for token-definition work, never in feature implementation.

</FoundationSection>

<FoundationSection title="What are design tokens?">

Design tokens are name and value pairings that represent small, repeatable design decisions. A token can be a color, a font style, a unit of white space or a corner radius made for one specific need.

For example, instead of picking one of many grays for helper text under a field, apply `color/text/subtle`. It is the same decision everywhere the app shows helper text, in every theme.

<FoundationExample caption="The helper line takes color/text/subtle: var(--ds-text-subtle).">
<div style={{ display: 'flex', flexDirection: 'column', gap: 'var(--stack-sm)' }}>
    <span style={{ font: 'var(--body-default)' }}>School</span>
    <span style={{ font: 'var(--body-small)', color: 'var(--ds-text-subtle)' }}>Choose the school the student attends.</span>
</div>
</FoundationExample>

</FoundationSection>

<FoundationSection title="What are themes?">

A theme is a collection of token values designed to achieve a certain look. In Figma a theme is a variable mode: switching the mode re-resolves every token bound on the frame. `color / semantics` was named `color / foundations`, and `spacing / layout` is dissolved: its breakpoint values now sit on the semantics or patterns token that owns them.

    head={['Collection', 'Modes', 'What changes']}

</FoundationSection>

<FoundationSection title="Why use design tokens?">

- Dark and high-contrast themes, and responsive layouts, work by swapping token values, not by redrawing screens.
- Designers and developers share one name per decision, which cuts handoff questions.
- When the visual language changes, the change is made once in the token, not found and replaced in every file.
- Color and spacing are generated in the repo and pushed to Figma: one plan per family holds every tier, and Figma follows.

</FoundationSection>

<FoundationSection title="Primitives and semantic tokens">

Primitives are the raw palette and scale. Every tier above them gives a step a job. Features only ever use those tiers, never a primitive.

- Primitives live in `color / primitives` and `spacing / primitives`. They are hidden from publishing and used only to define the tiers above. They have no meaning, so a primitive cannot respond to a theme.
- Semantic, pattern and component tokens live in `color / semantics`, `color / opacity`, `typography`, `spacing / semantics`, `spacing / patterns` and `spacing / components`. Each aliases a primitive, and in `color / semantics` each mode aliases a different one.
- The one exception is the Logo: its brand artwork reads palette primitives so it looks the same on every surface.

</FoundationSection>

<FoundationSection title="How to read design token names">

Knowing how to read token names helps you find the right token faster in a design and in code. A token's name describes how it should be used, and each part communicates one piece of that.

- Foundation: the kind of visual attribute, such as color, elevation or space.
- Property: the UI element the token applies to, such as text, border, background or surface.
- Modifier: extra detail such as a color role, emphasis or interaction state. Not every token has one: `color/text` is the default body text color.
- Pattern tokens read `Collection/property-variant`, for example `Card/radius-sm`: the Card pattern, its radius, the small variant.
- Numeric steps: the number is the rem value × 100 with zero padding, so 050 = 0.5rem = 8px and 100 = 1rem = 16px. A fractional step keeps the extra digit: 0625 = 0.625rem = 10px, 03125 = 0.3125rem = 5px, 00625 = 1px.

        [<C>color/border/focused</C>, 'color', 'border', 'focused', <C>var(--ds-border-focused)</C>],
        [<C>elevation/surface/raised</C>, 'elevation', 'surface', 'raised', <C>var(--ds-surface-raised)</C>],

Names look different in different tools. In code a color token drops its foundation and a trailing default and gains the `ds` prefix; a pattern token lowercases the collection and joins with dashes.

</FoundationSection>

<FoundationSection title="The four-tier ladder">

Every token sits on one of four tiers, most general to most specific, one Figma collection each and the same in code. One plan per family defines them (`scripts/lib/tokens/plan.mjs` for spacing), and `architecture/token-tiers-name-map.md` lists every token by tier.

<RefTable
    head={['Tier', 'Figma collection', 'Holds', 'Code']}
    rows={[
        ['Primitives', <C>spacing / primitives</C>, 'Space, Radius, Stroke and Size ladders, ×16 numbering', <><C>--space-*</C> · <C>--radius-*</C> · <C>--stroke-*</C> · <C>--size-*</C></>],
        ['Semantics', <C>spacing / semantics</C>, 'Pad, Stack, Inline, Radius (the safety net: steps only, no density), Border, Focus, Grid, Screen, Content and Size roles', <><C>--pad-*</C> · <C>--stack-*</C> · <C>--inline-*</C> · <C>--radius-*</C> · <C>--border-*</C> · <C>--focus-ring-*</C> · <C>--grid-*</C> · <C>--screen-*</C> · <C>--content-*</C></>],
        ['Patterns', <C>spacing / patterns</C>, 'Frame (Sidebar), Page, Section, Card, Table, Backdrop, Modal, Popover, Drawer, Panel, Focused page. Density (default, compact, spacious) lives here.', <><C>--frame-*</C> · <C>--page-*</C> · <C>--card-*</C> · <C>--modal-*</C> · <C>--blanket-*</C> · …</>],
        ['Components', <C>spacing / components</C>, 'A value exactly one component needs that no shared token covers (Button radius, Calendar day sizes, Checkbox and Radio control sizes, Listbox limits). Density here too.', <><C>{'--<component>-*'}</C>, e.g. <C>--button-radius-default</C></>],
    ]}
/>

`layers` (z-index) is its own family outside spacing: `--layer-*` (card, dialog, flag, modal, navigation, popup, backdrop, spotlight, tooltip).

**Fallback rule.** Reach for a component token first; if none fits, the pattern collection; failing that, semantics. The test for a pattern token: would the value change if the pattern changed? If yes, it belongs to the pattern (or the component); if the value is a shared step nothing specific owns, it is semantics.

**Current names only.** Outside `specs/` the code reads only the names on this ladder, and `npm run check:old-system` keeps it that way.

</FoundationSection>

<FoundationSection title="Using tokens in code">

Bind the token and nothing else. A token never takes a fallback, and the layer comes from what the thing is.

- A token is used bare: `var(--ds-text)`, never with a second value after a comma. That fallback is a fifth, unthemed color: it hides a missing token and drifts from every mode.
- Pick the tier by what the thing is. A session card takes the Card pattern (`--card-pad-default`); a filter chip takes the semantic Pad step (`--pad-x-md`).
- Spell tokens and copy in American English: gray, color, behavior.

**Use the token bare.** A helper line under a field.

<DoDont>
<Do caption="The token alone. A missing token fails loudly in review."><C>color: var(--ds-text-subtle);</C></Do>
<Dont caption="A hex written in place of the token keeps working in one mode only, so the drift is never noticed."><C>color: #626f86;</C></Dont>
</DoDont>

<FoundationSubsection title="Using tokens in design">

Bind a variable instead of a style value: select the layer, open the fill, stroke, radius or gap field and pick the variable by name. Set the mode on the frame to see another theme; every bound token re-resolves. Search the picker with the Figma name (`color/text/subtle`).

</FoundationSubsection>

<FoundationSection title="Do and don't">

<FoundationSubsection title="Choose by meaning">

Choose tokens based on meaning, not on a specific value.

<DoDont>
<Do caption="Use the token whose name and description fit the situation: helper text is text, subtle.">
<span style={{ font: 'var(--body-default)', color: 'var(--ds-text-subtle)' }}>Helper text under a field</span><br /><C>color/text/subtle</C>
</Do>
<Dont caption="Don't use a token because the color appears to match. It will not switch in Dark or the high-contrast modes.">
<span style={{ font: 'var(--body-default)', color: 'var(--ds-text-subtle)' }}>Helper text under a field</span><br /><C>neutral/800 (a primitive)</C>
</Dont>
</DoDont>

</FoundationSubsection>

<FoundationSubsection title="Never bind a primitive in a component">

Features bind semantic tokens. A primitive is a building block that only defines semantic tokens.

<DoDont>
<Do caption="The card follows any change to the card radius.">
<div style={{ padding: 'var(--card-pad-compact)', borderRadius: 'var(--card-radius)', background: 'var(--ds-surface-raised)', boxShadow: 'var(--ds-shadow-raised)', font: 'var(--body-small)' }}>Session card<br /><C>Card/radius (semantic)</C></div>
</Do>
<Dont caption="The same 16 today, but it stays put when the card radius changes.">
<div style={{ padding: 'var(--card-pad-compact)', borderRadius: 'var(--radius-100)', background: 'var(--ds-surface-raised)', boxShadow: 'var(--ds-shadow-raised)', font: 'var(--body-small)' }}>Session card<br /><C>Radius/radius-100 (primitive)</C></div>
</Dont>
</DoDont>

</FoundationSubsection>

</FoundationSection>

<FoundationSection title="Accessibility">

- Color pairs in `color / semantics` are checked per mode, including Light IC and Dark IC, so choosing by meaning keeps text and borders at the contrast the theme intends.
- Hard-coded or primitive colors skip that check and can fail in another theme.
- Test a screen in every color mode before shipping, not only Light.

</FoundationSection>
