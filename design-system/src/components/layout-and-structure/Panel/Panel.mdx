## Usage

Use `Panel` for context or a focused task beside the page's main content — a
detail view opened from a list, a filter set, a secondary thread — where
leaving the page behind, as a `Modal` does, would lose that context. For
something that must be decided before the page continues, use `Modal`
instead.

Fixed action components cover the common icons: `PanelBackAction`,
`PanelCloseAction`, `PanelMoreAction`, `PanelUpAction`, `PanelDownAction`,
`PanelNewTabAction` and `PanelViewSwitcher`, each a labeled `IconButton` with
its glyph and accessible name already set.

</div>

<div className="sb-ds-doc-section">

## Parts

1. **Container** (`PanelContainer`). The outer surface. Its `width` falls back to the nearest `PanelProvider`'s width, then to `--panel-width-default` (400); inside the Frame's Panel area it fills the area instead.
2. **Header** (`PanelHeader`). An optional back action, an optional title icon, the title, and an action group (close, more, …).
3. **Subheader** (`PanelSubheader`). An optional row of secondary content under the header: tabs, a filter summary.
4. **Body** (`PanelBody`). The main content, which scrolls.
5. **Footer** (`PanelFooter`). Actions that commit a change, with an optional `PanelDisclaimer` for small print beside them.

## Best practices

Use a panel for context or a focused task beside the page's main content.

### Give the panel room to read.

Below its default width the title wraps and the body stops being scannable.

<DoDontPair
    doExample={<DemoPanel />}
    doCaption="Default width."
    dontExample={<DemoPanel width="calc(var(--panel-width-default) / 3)" />}
    dontCaption="Squeezed to a narrow strip."
/>

### Keep the header to one cue.

An icon, a subheader and a footer together bury the title; pick the one the task needs.

<DoDontPair
    doExample={<DemoPanel titleIcon={panelIcon} />}
    doCaption="Title with an icon."
    dontExample={<DemoPanel titleIcon={panelIcon} subheader="Thursday, 4:00 PM" backAction={<PanelBackAction />} />}
    dontCaption="Icon, back action and subheader all on, burying the title."
/>

### Title the panel with the object.

The title names what the panel shows, so someone who opened it from elsewhere still knows.

<DoDontPair
    doExample={<DemoPanel title="Session notes" />}
    doCaption="The object it shows: “Session notes”."
    dontExample={<DemoPanel title="Details" />}
    dontCaption="A generic “Details” that does not name the object."
/>

### Share one width across a page's panels with `PanelProvider`.

Wrap the region that can open panels in a `PanelProvider`, and read or change
the shared width with `usePanelManager`, so multiple panels opened over time
stay the same size instead of each picking its own.

```jsx
<PanelProvider>
    <PanelContainer>
        <PanelHeader title="Student detail" actions={<PanelCloseAction onClick={close} />} />
        <PanelBody>...</PanelBody>
    </PanelContainer>
</PanelProvider>
```

### Reach for the fixed action components before building your own.

`PanelBackAction`, `PanelCloseAction` and the rest already carry the right
icon, label and compact spacing — building a custom `IconButton` for the same
job only risks a different icon or label than the rest of the system uses.

## Accessibility

- **A labeled region.** `PanelHeader`'s title is a `Heading`, giving the
  panel a heading assistive technology can navigate to directly.
- **Fixed actions are already named.** Each action component sets its own
  accessible name (for example, `PanelCloseAction` is always labeled
  "Close"), so there is nothing extra to pass.
- **`usePanelManager` outside a provider fails loudly.** Calling it without a
  `PanelProvider` ancestor throws, rather than silently falling back, so a
  missing provider is caught during development.
