### Heading levels

**The tag is the outline position. The class is the appearance.** A heading that
has to *look* small but sit high in the page's outline is written
`<h2 className="h4">`, not `<h4>`.

This works because `design-system/src/tokens/_fonts.scss` declares every heading
step against **both** selectors at once — `h4, .h4 { … }`, `h6, .h6 { … }`, and
so on for all six. Font family, size, line height, weight and the nested
FontAwesome sizing are one rule shared by the tag and the class, so moving a
heading to a different tag and keeping its `hN` class leaves its rendered size
byte-identical. Nothing else in the system needs to change.

Two consequences worth stating outright:

- **A heading with no size class takes its appearance from its tag**, and the
  steps are not interchangeable — `h1`–`h3` are `%font-headline` (weight 700),
  `h4`–`h6` are `%font-title` (weight 600), and every step has its own line
  height. So re-tagging a bare `<h3 style={{ fontSize: '14px' }}>` silently
  changes its weight and leading. Give it the class of the tag it is leaving
  (`<h4 className="h3" style={…}>`) in the same edit.
- **CSS that selects a heading by tag re-couples the two.** A rule like
  `.lesson-content__question h4 { … }` stops applying the moment that heading's
  outline position is corrected. Where such a rule exists, match the size class
  as well: `h4, .h4 { … }`.

What this rules out is choosing a level for its size. 329 `<h6>` against 5
`<h1>` across `specs/` was `h6` being used as small bold text; a page then ran
`h2` → `h6` and axe's `heading-order` reported the three skipped levels. The
level a heading carries is decided by where it sits in *its own page's* outline,
so a shared component that lands at different depths takes the level as a prop —
`OverviewCard`'s `titleAs` is the pattern.

The same separation covers text that is not a heading at all. A metric drawn at
display size is not a section: `<p className="h4">Answered Correctly</p>` in
`LessonsDetailPage` is how that text gets heading type without taking an outline
slot. The values still marked up as `<h1>`/`<h3>` beside it are #244.

The docs view used to break this separation. `.sbdocs h1 / h2 / h3–h6 { …
!important }` in `.storybook/storybook-overrides.css` reached into story
canvases — `.docs-story` sits inside `.sbdocs` — and forced every heading a
component rendered to one of three docs sizes, so `<h3 className="h6">` drew at
28px instead of 16px and the preview was not showing the component. Those rules
are now fenced with `:not(:where(.docs-story *))` and apply to MDX prose only
(#244). Any new `.sbdocs hN` rule needs the same fence.

</div>

### The top of the outline

**Every page's outline starts with an `<h1>`.** The rule above places a heading
*within* an outline; this one says the outline has a top at all. They are
separate defects with separate causes, and only one of them is something axe can
report. (Starts with, not "has exactly one": a story that renders the same page
twice, or a lesson's completion screen, legitimately shows more than one.)

`heading-order` flags a heading that jumps more than one level below its
predecessor. The **first** heading on a page has no predecessor, so a page whose
whole outline reads `h4 → h4 → h4` satisfies the rule and still has no top. That
was 111 of 114 page stories before #243.

`page-has-heading-one` is the rule for exactly this, and it never runs here: axe
evaluates its page-level rules only when the run context is the whole document,
and `addon-a11y` scopes every run to the story root. No page-level rule appears
anywhere in `docs/evals/a11y-baseline.json` — not because they pass, because
they are never evaluated.

So it is guarded by two things that are not the baseline:

- `.storybook/page-outline.js` asserts, in the browser suite, that every page
  story renders an `<h1>` and that no other heading precedes it. A failure is
  blocking, not ratcheted.
- `npm run check:page-outline` holds the half that assertion cannot: that its
  title-based selector still picks out exactly the story files under
  `specs/**/Pages/**` plus the three area overviews, that the population has not
  shrunk, and that the assertion is still registered in
  `.storybook/vitest.setup.ts`.

**Where the `<h1>` comes from.** `PageLayout` takes a `title` and renders it as
the first element inside `<main>`, visually hidden — these pages put their name
in the TopBar breadcrumb rather than in the content, so a visible title would be
a design change, and 41 of the 42 page stories reach their `<h1>` this way from
one prop. It is hidden off-screen and **never** with `display: none`, which
would take it out of the accessibility tree and leave the page with no top at
all. A page that renders its own visible title heading — `LoginPortal`'s
"Login", the area overviews' "Admin Organisms" — marks *that* heading up as the
`<h1>` and leaves `title` unset, rather than carrying two.

**A fragment is not a document.** An `<h1>` in a `Badge` story would be wrong.
The population is `specs/**/Pages/**` plus the area overviews, and it is written
down in `scripts/check-page-outline.mjs` rather than inferred.

**Adding the `<h1>` moves everything under it.** An `h1` followed by an `h4` is
a three-level skip, so a page that used to run `h4 → h4` has to become
`h2 → h3` — tag only, class kept, nothing changes on screen. Two consequences,
both of which bit during #243:

- A component that lands at two depths takes its level as a prop.
  `SectionTitle` is an `h3` under a page's own header and an `h2` on the
  Reflection page, which has no such header.
- Tag-keyed CSS has to be widened in the same edit, exactly as § Heading levels
  says. `.lesson-content__title-section h4` silently dropped a colour and a
  margin the moment those titles became `h2`.

### Contrast

Text and icon colors are paired with their surface tokens so contrast is
guaranteed by the palette, not checked per-component:

Never place `on-surface` colors on accent fills or vice versa — always use the

### Focus states

Per the Pattern System's universal interaction logic, focus is an **additive
overlay** — it never replaces the base fill:

- Overlay `on-surface` at **12% opacity** (`--color-on-surface-state-12`) on top of the base fill.
- Change the border to **Inverse Primary** (`--color-inverse-primary`).
- Component opacity stays at 100%.

This gives every interactive element (buttons, cards, table rows, list items) a
visible, consistent focus indicator in both themes.
</div>

<div className="sb-ds-doc-section">
### Disabled states

Disabled components are set to **38% total opacity**
(`--color-disabled-opacity: 0.38`), applied to the whole component rather than
recoloring individual parts. Disabled elements are not focus targets.
</div>

### Charts

Every chart in Data visualizations is a Highcharts wrapper, and they all share
`dataviz/chartTheme.js`. Two settings there carry the accessibility contract, so
a chart built on the theme needs no per-component work:

- **The accessibility module is on.** Highcharts only describes itself when
  `accessibility.enabled` is true — it then emits a screen-reader section naming
  the chart type and axes, labels every series and point, and makes the data
  keyboard-navigable. With it off, Highcharts falls back to stamping the SVG
  `role="img"` with a label read off the chart title; since these charts render
  no title, that label was empty and every chart announced as an unlabeled
  image.
- **Charts are groups, not landmarks.** `landmarkVerbosity: 'disabled'` keeps
  the chart a labelled `role="group"` instead of a `role="region"` landmark. A
  chart here is a widget inside a page region, not a region of its own, so a
  dashboard with six charts adds six groups rather than six entries to the
  landmark menu.

A chart that assembles its own options instead of spreading `chartTheme` has to
carry `accessibility: chartTheme.accessibility` itself. Do not wrap a chart in
`aria-hidden` to quiet a labelling warning — that hides the keyboard-navigation
proxies the module creates, which is a worse defect than the one it silences.
</div>

### Automated checks

The a11y addon (`@storybook/addon-a11y`) is enabled in `.storybook/main.js` and
runs axe checks inside story tests. To run the checks for a set of stories:

```bash
npx vitest --project=storybook --run <path>
```

Violations surface in the test UI (the `a11y.test` parameter in
`.storybook/preview.jsx` controls whether they are advisory or fail CI).
