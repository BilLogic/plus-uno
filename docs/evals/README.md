# evals/ — the quality loop (L4)

Criteria, tests, fixtures, results — one folder, one loop.

| Dir | Holds | Rule |
|---|---|---|
| `rubrics/` | what "good" means, one rubric per artifact type (PRD, prototype, share-out, lesson, skill, agent-spec, bot-answer D1–D9) | YAML criteria + prose rationale; applied by `reviewers/rubric-applier` |
| `scenarios/` | `<skill>.md` — ≥3 scenarios (query + expected behavior) per skill | **written BEFORE the skill body** (evals-first); baseline without the skill, then write the minimal skill that passes |
| `fixtures/` | frozen golden inputs + answer keys per skill (see fixtures/README.md) | benchmarks run against these — a moving fixture measures nothing |
| `runs/` | `*.jsonl` — one line per scored run, plus `apply-log.jsonl` (one row per executed Flow-5 verdict: target · verdict link · timestamp) | interim store until the Notion Eval Runs DB exists; written at flow exits |

**Where a uno-bot eval run lands.** `run-evals.mjs` writes `eval-results.json` to the repo root — every case's verdict, its `passedRuns/samples` tally, its deterministic failures, the judge's reason, the subject the board handed it, and the full transcript of every turn. **A row has one shape (#617).** It used to be whichever of five hand-built literals the walk reached — an unreachable case, a failed subject read, an unsatisfiable condition, an unfilled placeholder, a case that ran — each naming only the keys its own branch cared about, so `pass` was absent on three of them and `judged` on four, and no reader could tell "this case did not fail" from "this branch never wrote the field". `agents/uno-bot/scripts/eval-results.mjs` is the one constructor: every key, every row, and a key outside its vocabulary is refused the way `eval-case.mjs` refuses a fixture key. That module also holds the run's GATE: a failed blocker is an error and a failed non-blocker a warning, and the shared findings interface (`scripts/lib/findings.mjs`) renders them and decides the exit code — so the eval suite fails the way every other check in this repository fails. The per-case log above it is untouched, which is why the registry keeps this check spawn-shaped: a line per case across 34 cases is exactly the shape findings rendering would flatten. `.github/workflows/uno-bot-evals.yml` uploads that file as the `eval-results` artifact on every run, pass or fail, so a red blocker can be read rather than re-run. Each turn's `tools` list carries every call the model made with the arguments it sent, and — since 2026-09-05 with #452 — what each RESULT said about itself: `note`, `visibility`, `error`, and nothing else. Never rows, never message or blueprint content: an artifact is a file that outlives the run, and results in it would be the S2 disclosure failure moved into the instrument. The three fields are what a search-shaped failure is diagnosed from — S3 read 0/3 against r254 with all three replies saying workspace search "isn't available on this turn", and the artifact could not say which leg produced it. Nothing is written to `runs/` by this suite; that directory is the skill flows' store.

**How a turn is run is a dependency (#511).** `run-evals.mjs` takes a TURN TRANSPORT — `{ runTurn({ prompt, history, pending, surface }), fetchSubject?(need, case) }` — and `--transport=worker` is the default, so the cron's plain `node agents/uno-bot/scripts/run-evals.mjs` means what it always meant: a POST to the deployed Worker's `/debug/eval` route, now `workerTransport` in `agents/uno-bot/scripts/eval-transport.mjs`. `WORKER_URL` and `DEBUG_TOKEN` are required by that transport, not by the runner. The summary records which transport answered, because scores produced in-process and scores produced against a deployment are different measurements and nothing else in the file tells them apart. Everything the runner does between the turns — the fixture walk, the subject substitution, the deterministic checks, the history threading, the sampling arithmetic — is transport-agnostic and is exercised by `agents/uno-bot/scripts/run-evals.test.mjs`, which replays real fixture cases (R3, C1, B2) through a fake transport under `node --test`; the in-process adapter that calls the Worker's Turn module directly is `--transport=local`, below. **Who grades is a dependency too, and the same shape.** A judge is `{ name, judgeCase(case, transcript) }` and `agents/uno-bot/scripts/eval-judge.mjs` owns the whole of it: the rubric, the service-account credential, the Vertex call, the transcript cut and the fail-open. `judgeFromEnv()` returns the Vertex judge when `GEMINI_SA_EMAIL`/`GEMINI_SA_PRIVATE_KEY` are present and exchange, and a judge that skips every case when they are not — so a run with no credential has fewer verdicts, not a crash, and the runner's default is a judge rather than a null. Every path out of `judgeCase` is `pass`, `fail` or `skipped`; a judge that cannot be reached, cannot be parsed, or was never given a credential must not turn the suite red, because the deterministic checks still ran and a network hiccup is not evidence about the bot. **A skip is not a pass, and the run says which it was (#618).** Failing open leaves a skipped case green, so on its own it is indistinguishable from a case the grind model read and approved: every skip therefore carries its REASON (`judgeSkipped` is the only constructor for one), every result row carries `judged`, and the summary carries a `judge` stanza — the judge's name and a count per verdict with the reason behind each skip, printed beside the score as `0 judged (0 pass, 0 fail), 34 unjudged — 34× credential could not be exchanged for a token`. The no-credential judge names its own reason, because an absent service account and an expired one both land there and only one of them is somebody's Monday morning. The tally counts one verdict per case, as `passed` and `failed` do, and a case that failed its deterministic checks or never ran is `not asked — …` rather than a fail the judge returned. **The judge's rubric has one home**: it is loaded from `rubrics/bot-answer.md` and its `dimensions:` block is quoted into the judge prompt verbatim, so a dimension added or sharpened reaches the next run with no second edit — `eval-judge.test.mjs` fails when a D-id in the document does not reach the prompt, and exercises the credential, the cut and the fail-open with no network call. The condensed paraphrase the runner used to carry is gone.

**`--transport=local` runs the suite in-process, from recorded replies (#512).** `agents/uno-bot/scripts/eval-transport-local.mjs` calls the same `evalTurnRequest → runTurn → evalTurnResponse` path the Worker's route takes, with the same in-memory ThreadState seeded from the runner's history and the same recording Delivery — so no deployment, no `WORKER_URL`, no `DEBUG_TOKEN` and no model spend. The model is a **recording**: `fixtures/recordings/<case>.json` holds that case's model replies (and, where a case turns on one, what each lookup returned), replayed through the real agent loop behind the fake `ModelProvider`, so the loop's own rules — a side-effect call staged as a gated proposal, `proposal_resolve` authorized against the pending card — all run against a fixed draw. `fixtures/recordings/README.md` is the format; **`source: "authored"` vs `"captured"` is load-bearing** and reaches the results file's `build` field. How many cases are recorded, and how many are therefore **unreachable** on this gate, is the census block above — counted from `fixtures/recordings/`, never typed. The three that shipped with #512 were AUTHORED by hand — writing that ticket needed no Vertex credential, and a fabricated score is worse than a missing one — and the capture replaced them. So a local run measures **the turn** (the dispositions, the gate's idempotency, the cancel bounce, the history write) and measures **nothing about the model**; the Monday cron keeps `--transport=worker`, which is the run that does. `scripts/eval-record.mjs` captures the rest off a live `/debug/eval` when someone has credentials (`--case=ID`… or `--all`) — **and nobody needs to hold those credentials locally (#544)**: `.github/workflows/uno-bot-evals.yml` takes a `mode` input, so `gh workflow run uno-bot-evals.yml -f mode=record` records the whole suite from CI, where `WORKER_URL` and `DEBUG_TOKEN` already live, and `gh run download <id> -n eval-recordings` fetches what it wrote — to be read, then committed into `fixtures/recordings/` in its own PR. It is a dispatch and not a cron because a capture is one live billable model run per case; `mode: run` (the default, and the Monday cron) is unchanged. A case that declares a run-time `subject` is captured **with its row** (#541): the Worker's subject read answers first, the row fills the case's placeholders, and it is written into the recording as `subject`, so the local transport replays the case against the board it was recorded on — a recording without one skips by name, as a missing recording does. A case with no recording is reported **UNREACHABLE** — `transport.unsupported(case)` names the reason, the run's opening census names the case, the runner counts it apart exactly as it counts an unsatisfiable subject condition (#415), and it never fails a blocker: a gate that is red for "no recording" is a gate that gets switched off, and a skip nobody counts is a blocker that gates nothing while reading as though it did. **What runs on a pull request, and what does not.** `evals:local` is a composed registry row (`scripts/checks.registry.mjs`), so `npm run check:harness` runs it — locally and in `.github/workflows/check-harness.yml`, on every pull request, inside the `npm ci` that job already scopes to `agents/uno-bot`. That run has no credential of any kind, so **the judge is absent by construction** and only the deterministic checks decide: `expectKind`, `expectTool`, `forbidTool`, `expectDecision`, `textRegex`, `expectToolCalled`, `expectTier` and `expectLevel`. A failing BLOCKER exits 1 and fails the job; a case with no recording is reported **unreachable** and fails nothing, so "the gate is red" always means a turn changed, never that a recording is missing — and how much of the suite a green run stands for is in the summary's `unreachable` list rather than left to inference. The **judged** run is the other measurement and stays where the credentials are — the Monday cron and `workflow_dispatch` on `uno-bot-evals.yml`, `--transport=worker` against the deployment, D1-D9 scored by the grind model.

**The eval route is an ADAPTER over Turn (#499).** `/debug/eval` no longer runs a pipeline of its own. The 127-line driver that called `runAgent` directly — and mirrored production's clarify gate by calling `preflight` beside it, and stopped there — is deleted; the route builds a `TurnRequest` from the case body and hands it to the same `runTurn` a Slack message takes (`agents/uno-bot/src/eval/turn-adapter.ts`, with the pure request/response halves in `eval/turn-case.ts`). So an eval turn now passes through preflight, the confidence pre-check, the absence check, the draft judge, the gate's idempotency rules and the history write exactly as a designer's turn does — every guard that lives above the loop was previously invisible to the suite. **Both callers share one dependency builder and one request builder** — `agents/uno-bot/src/turn/env-deps.ts` and `src/turn/request.ts` — so the wiring cannot be hand-copied into two files and drift, which is what it had done: the agent run, the draft judge, preflight, the three cards, the antecedent read and the context-state flag were duplicated character for character while the header claimed two dependencies differed. Each adapter now names only its own differences, and the eval suite's are four: **Delivery records instead of posting** (`recordingDelivery` — no 👀, no working signal, no card in a real conversation); a **resolution is recorded instead of executed** (the old driver never executed one either; a suite that files a Notion card per sample is a suite nobody can run three times); **thread state is in-memory**, seeded with the history the runner sent, so the store-backed rules — the "(Cancelled the proposed …)" bounce, the compaction trigger — read the conversation production would; and the **reporters** an artifact is collected through (the dials, the tool calls, what each result said, what the gate asked, what the loop returned), which production reads its log lines for instead. `agents/uno-bot/tests/eval-adapter.test.ts` holds the parity, and holds it against the REAL builders on both sides: the same text as an eval case and as a Slack message builds the same request field for field, reads the same dependency list entry for entry, and produces the same `TurnOutcome`, the same Delivery calls and the same stored history. It used to compare the eval builder to a hand-written copy of the Slack request, which passed while production set three fields the copy omitted.

**The response shape is unchanged**, and its field names have ONE definition — `EVAL_RESPONSE_FIELDS` in `agents/uno-bot/src/eval/turn-case.ts`, the module that builds the envelope. This document used to carry the list too, beside a hand-copied array in `tests/eval-adapter.test.ts`: three copies of a wire contract, so a field could be added to the envelope and named nowhere. The test now reads the list, and fails in both directions — a field the envelope carries and the list omits, or the reverse (#617). Two fields mean something sharper than they did. `result.text` on an answered turn is the body that was **delivered** — after the confidence pre-check and the judge — where the old route reported the model's raw draft, so a `textRegex` assertion scored prose no designer would have read. And an `asked` turn reports the gated proposal plus `gateAsk` where the clarify gate asked (the pair `allowProposalIfGateAsk` reads, R8/R12), but reports the **text** where nothing was gated and nothing staged — the deterministic cancel bounce, which R5's turn 3 asserts as `expectKind: ["text"]`. One field is added: `turn` — the disposition, the tier, the route, the judge's verdict and whether a card was staged. Nothing reads it yet; it is the half the old driver could not report at all.

No case regressed; D1's one-in-three miss of the `read_reference` pointer on the old build reads three of three after; P2's single miss was a judge flake. The fixture expectations therefore stand as the post-adapter baseline, and the local transport's recordings (`fixtures/recordings/`) were captured off that same deployment.

The summary at the top of the file records **what was measured, and what measured it**: `workerBuild` — the `build` the `/debug/eval` route reported, i.e. the deployment that actually answered — and `fixture` — the checkout revision plus a hash of the fixture bytes as loaded. Both, because neither is inferable from the other: Actions checks out at depth 1 so a per-file `git log` is empty, and a locally-edited fixture is not the committed one. `passed` / `failed` / `skipped` are three counts, not two — a case whose run-time condition nothing on the board satisfied is skipped, and folding it into either of the others would describe a run that did not happen (#415).
