## When to use

Use `Input` for single-line text entry — names, emails, search boxes, anything
where the answer is one short string. It is the field that owns its own label,
its own validation state and its own message, which makes it the right home for
an error rather than an `Alert` at the top of the form.

`validation` takes `none`, `invalid` or `success`; pair it with
`validationMessage` and the component renders the message beneath the field with
a matching icon.

</div>

<div className="sb-ds-doc-section">

## Usage notes

- **A visual is decoration; it never carries the meaning.** `leadingVisual` and
  `trailingVisual` accept a Font Awesome class name or a node, and a string is
  rendered `aria-hidden`. Anything the reader must know — that this is a search
  field, that the value is a currency — belongs in the `label` or the
  `validationMessage`, not in the glyph.
- **`validationMessage` only renders when `validation` is not `none`.** Setting
  the message alone shows nothing, which is the shape to reach for when a field
  should carry its message only once it has failed.
- **The field points AT its message.** When both are set, the message
  gets an id and the input an `aria-describedby` naming it, alongside
  `aria-invalid` for `invalid`. A caller's own `aria-describedby` is kept and
  the generated id appended, so passing one does not silence the error.
- **The caption holds a message and a count.** `caption` is standing help;
  a `validationMessage` takes its place while `validation` is not `none`.
  `maxLength` adds a count on the right ("24 / 30"), beside either.
- **Set `autoComplete` on every field the browser can fill.** Login email is
  `email`, the password is `current-password`, and an access code is
  `one-time-code`. Extra props land on the input, so `autoComplete`,
  `pattern`, `inputMode` and the rest reach the control rather than its box.
- **`subtle` is for editing in place**, on record and profile pages, never in a
  form someone fills from top to bottom. Pass `onSave`; it is called on blur or
  Enter, Esc cancels, and while it runs Trailing shows "saving…". Throw or
  reject and the field stays open in `invalid`, keeping what was typed, with
  your error as the caption.
- **`type` is passed straight through.** `type="email"` and `type="tel"` change
  the mobile keyboard as well as the validation, which is worth setting even
  where the form validates server-side.

</div>

## Accessibility

- **The label is associated whether you pass `id` or not.** One id is derived
  once and used for both the label's `htmlFor` and the input; when no `id` is
  given, React's `useId` supplies one. Pass `id` when something outside the
  component needs to point at the input — an `aria-describedby`, a `<label>` you
  render yourself, a test selector — and you will get exactly the id you passed.
  `name` is a form key, not an id, and no longer stands in for one.
- **`showLabel={false}` hides the label, it does not remove it.** The label is
  rendered either way and always carries `htmlFor`; `showLabel={false}` only
  clips it out of sight with `.plus-field-label--hidden`. So a field that has a
  `label` has an accessible name whether or not you show it, and turning the
  label off costs nothing but the pixels. See *Why `showLabel` cannot take the
  name away* below.
- **`required` shows an asterisk and sets `aria-required`.** The asterisk is
  hidden from assistive technology, which hears "required" from the input. The
  form explains the asterisk once, in a legend above the fields; there are no
  "(optional)" marks. The browser's own `required` is not set, so the form
  decides when to validate.
- **`info` puts a tooltip button beside the label**, outside the `<label>`, so
  its name is never part of the field's name.
- **`validation` is announced, not only drawn.** The message gets an id, the
  input points at it with `aria-describedby`, and `validation="invalid"` sets
  `aria-invalid` and renders the message with `role="alert"`, so it is read out
  when it appears. A `success` message describes without claiming an
  error. Your own `aria-describedby` is kept and the message id is appended, so
  standing help and a new error are both read, in that order.
- **A field with no `label` still has no name.** `showLabel` decides whether the
  label is *seen*, not whether there is one. If the visible label is rendered by
  the caller instead — a `<Label>` above the field, a table column header — point
  it at the input with `htmlFor`; if there is no text anywhere, pass `aria-label`.
- **Everything else passes through.** `type`, `autoComplete`, `maxLength`,
  `pattern`, `inputMode` and any `aria-*` attribute all reach the input element,
  so the native affordances are available even though the wrapper does not use
  them.

### Name the field, even when the design shows no label.

```jsx
// Incorrect — a placeholder is not a name, and it disappears as soon as
// someone types.
<Input placeholder="Search tutors" />

// Correct — the label names the field; showLabel={false} only hides it.
<Input label="Search tutors" showLabel={false} placeholder="Search tutors" />
```

### Explain the asterisk once, not on every field.

```jsx
// Incorrect — "(required)" in every label, and an asterisk as well.
<Input label="School (required)" required />

// Correct — the asterisk, with one legend above the form:
// "Fields marked * are required."
<Input label="School" required />
```

## Why `showLabel` cannot take the name away

`showLabel={false}` used to skip rendering the label entirely, which raised
the question of whether that mode should exist at all, since a component that
makes "no accessible name" easy keeps producing the defect. The 37 call sites answered it,
and they were not one population:

- **17 pass a real `label` string and then switch it off** — the whole Login
  family (`LoginPortal`, `InstitutionSelection`, `InstitutionForm`,
  `AccessCodeForm`) and the prototype-market search field. The name was already
  written; the design just has no room to show it. These never wanted "no
  label", only "no visible label".
- **19 pass no `label` at all**, because the caller renders its own visible
  label above the field — the Profile sections do this throughout, with the
  `Label` element from Label and caption. `showLabel={false}` there prevents a
  *second* label, which is a real and correct use. Removing the prop would put a
  duplicate label back on every one of those fields.
- **1 is a search box inside `Select`'s dropdown**, named by the listbox it
  filters.

So neither answer was right on its own. Forbidding the mode breaks
the 19; permitting it as-is leaves the 17 one careless call site away from an
unnamed field forever. The resolution is to make the mode mean something it can
be trusted with: **`showLabel` is a visual switch, and the accessibility tree
does not read it.** The 17 gained a name with no visual change and no call-site
edit; the 19 are untouched, because a `label` you never passed is still not
rendered. What is left is the one honest way to have no name — pass no text at
all — which is true of every component in the system and is not something
`Input` makes especially easy.

The half that `Input` cannot fix is the 19: a label rendered outside the
component has to be pointed at the input by the caller. Seventeen of them pass
`htmlFor` — the Profile sections and the tutor profile page — because each names
one control.

The last two were `DateAndTimePicker`s under a single shared caption, where
`htmlFor` was never available: one `<label for>` names one control, and that
field renders two. They were settled from the other end. The visual switch was
ported — `DateAndTimePicker`'s `showLabel` now clips its label instead of
deleting it, same clipping, same reasoning — and each picker was given its own
`label` to clip, so the two controls are named "Start time" and "End time"
rather than both being called "Time". The visible caption stopped competing for
that job and names the pair as a `group`. In both components the name now
belongs to the component; text the caller renders above the field is a caption,
not a second claim on the name.

## Related

- For multi-line text, use `Textarea`.
- For numbers with steppers, use `NumberInput`.
- For a value chosen from a list, use `Select`.
- For dates, use `DatePicker` or `DateAndTimePicker`.
- For an input with an attached button or addon, use `InputGroup`.
