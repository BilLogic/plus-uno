# evals/ — the quality loop (L4)

Criteria, tests, fixtures, results — one folder, one loop.

| Dir | Holds | Rule |
|---|---|---|
| `rubrics/` | what "good" means, one rubric per artifact type (PRD, prototype, share-out, lesson, skill, agent-spec, bot-answer D1–D9) | YAML criteria + prose rationale; applied by `reviewers/rubric-applier` |
| `scenarios/` | `<skill>.md` — ≥3 scenarios (query + expected behavior) per skill | **written BEFORE the skill body** (evals-first); baseline without the skill, then write the minimal skill that passes |
| `fixtures/` | frozen golden inputs + answer keys per skill (see fixtures/README.md) | benchmarks run against these — a moving fixture measures nothing |
| `runs/` | `*.jsonl` — one line per scored run, plus `apply-log.jsonl` (one row per executed Flow-5 verdict: target · verdict link · timestamp) | interim store until the Notion Eval Runs DB exists; written at flow exits |

**Where a uno-bot eval run lands.** `run-evals.mjs` writes `eval-results.json` to the repo root — every case's verdict, its `passedRuns/samples` tally, its deterministic failures, the judge's reason, the subject the board handed it, and the full transcript of every turn. `.github/workflows/uno-bot-evals.yml` uploads that file as the `eval-results` artifact on every run, pass or fail, so a red blocker can be read rather than re-run. Each turn's `tools` list carries every call the model made with the arguments it sent, and — since 2026-09-05 with #452 — what each RESULT said about itself: `note`, `visibility`, `error`, and nothing else. Never rows, never message or blueprint content: an artifact is a file that outlives the run, and results in it would be the S2 disclosure failure moved into the instrument. The three fields are what a search-shaped failure is diagnosed from — S3 read 0/3 against r254 with all three replies saying workspace search "isn't available on this turn", and the artifact could not say which leg produced it. Nothing is written to `runs/` by this suite; that directory is the skill flows' store.

The summary at the top of the file records **what was measured, and what measured it**: `workerBuild` — the `build` the `/debug/eval` route reported, i.e. the deployment that actually answered — and `fixture` — the checkout revision plus a hash of the fixture bytes as loaded. Both, because neither is inferable from the other: Actions checks out at depth 1 so a per-file `git log` is empty, and a locally-edited fixture is not the committed one. `passed` / `failed` / `skipped` are three counts, not two — a case whose run-time condition nothing on the board satisfied is skipped, and folding it into either of the others would describe a run that did not happen (#415).
