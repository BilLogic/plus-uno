## For developers

- **Pass the buttons either way.** Use the <code>buttons</code> array of configs, or Button children. Children win when both are given.
- **The group hands its <code>size</code>, <code>style</code> and <code>fill</code> down** to every child that does not set its own. Children are cloned and not checked, so a non-Button child receives those props too.
- **Group-level <code>style</code> is a narrower set than Button's.** The five pillar styles are not valid on the group. Keep the group on a semantic style and override <code>style</code> on one segment.
- **Show a selected segment with <code>aria-pressed</code>.** <code>active</code> adds a class and nothing else, so declare the state through a config's <code>props</code> object: <code>props: aria-pressed</code> set to whether that segment is chosen.

## When to use

Use a Button group when a few actions work on the same thing. Join two to five peer actions on one object, such as Day, Week and Month on a calendar. A single action is a [Button](?path=/docs/components-forms-and-inputs-button-button--docs), and picking one value from a short scale is a [Choice group](?path=/docs/components-forms-and-inputs-choice-group--docs).

- **Group only actions that belong together.** A group says its buttons act on the same thing. Unrelated actions side by side belong in separate Buttons with space between them.
- **Keep it to two to five segments.** One segment is just a Button. Past five, the labels shrink and the group reads as a toolbar, so use a menu for the rest.
- **Use one style and size across the group.** The segments share their style and size from the group. Restyle one segment only to show the selected one.
- **Place dialog and card footer buttons directly.** The connected treatment implies the actions are alternatives.

</div>

## Accessibility

- **Name the group.** The group has the role group, and <code>ariaLabel</code> is the only prop that names it. An unnamed group adds a boundary with no explanation, and a screen reader announces only "group".
- **Tab moves between the buttons**, one stop each. That suits a toolbar of actions and not a segmented picker, which is the reason a picker belongs in a Choice group.
- **A selected segment needs <code>aria-pressed</code>.** A row of buttons announces no selected state on its own.
- **The buttons keep their own rules.** Sizing, icon-only naming and the disabled behavior on the Button page all still apply inside a group.
