## Usage

Use `Modal` when the next step has to happen before anything else can: a
destructive confirmation, a short form that would derail the page, a detail view
the person closes and returns from. It is the one messaging component that takes
focus from the page, so it fits when interrupting is the point.

The footer runs on `FooterActions`: pass `primaryButton` and `secondaryButton`
as objects for a `50/50` pair (or `primaryButton` alone for the right half), or
pass `footer` with `<FooterActions>` for three actions or a leading text
button. Opening a Modal closes a floating Sidebar; a docked one stays.

### Width guidance

`width` takes a step of `MODAL_WIDTHS`{` (${MODAL_WIDTHS.join(' · ')})`}: that
many columns of the screen grid plus the modal pad.

The Modal draws `--ds-surface-overlay` with `--ds-shadow-blocking`, in every
type and width: it is the one surface that sits on a Blanket, so it lifts higher
than a menu. A `Select` list opened inside it keeps `--ds-shadow-overlay`.

The width grows with the screen, never shrinks, and ignores the Sidebar. The
height hugs its content up to the cap the Blanket sets
(`--blanket-max-height-modal`); `height="fill"` sits at that cap.

## Alternatives

- For a message the person only reads, use `SectionMessage` in the page or `Flag` at the screen corner.
- For a task that takes more than a screen or has sections, use `Frame`: the focused template, with no sidebar.
- For a task that keeps the page in view, use `Panel`, floating: a row's details, filters, a short edit.
- For a small aside anchored to a control, use `Popup`.
- For a list of actions or a value to pick, use `DropdownMenu` or `Select`.

## Parts

1. **Blanket.** Dims the page and holds focus inside.
2. **Header.** Title, optional description, header actions and the close button.
3. **Body.** Text or any content; scrolls when it overflows.
4. **Footer.** Appears only when a button or `footer` is given: `FooterActions` divides the width inside container padding into four equal tracks.
5. **Dividers.** Optional rules under the header and over the footer.

The tokens each part draws are read from `Modal.scss` and listed under Tokens
touched in the Harness tab.

## Footer actions

`Modal` places its footer actions inside <DocsLink id="components-forms-and-inputs-button-footer-actions">FooterActions</DocsLink>, sharing one four-track contract with <DocsLink id="templates-panel">Panel</DocsLink> and <DocsLink id="templates-frame">focused views</DocsLink>. Secondary buttons draw the `default` soft neutral fill (`--ds-background-neutral`) with no outline.

1. **Four equal tracks.** `FooterActions` divides the width inside the modal padding into four equal tracks with an `--inline-md` gap; every track button uses `spacing="spacious"` (`48` high) and `shouldFitContainer`.
2. **One button.** Takes the right half (tracks `3` and `4`), or all four tracks when the container is `4` columns (`400`) wide or narrower.
3. **Two buttons.** Split `50/50` across the full width (tracks `1`–`2` and `3`–`4`): secondary on the left in the `default` soft neutral fill (`--ds-background-neutral`), `primary` on the right.
4. **Three buttons.** Take one quarter each in tracks `2`, `3` and `4`; only the rightmost is `primary`.
5. **Leading text button.** A text action (such as a danger "Delete session", or a `subtle` "Not now" or "Skip") hugs the left content edge and never takes a track; the filled buttons then sit in tracks `3` and `4`.
6. **Destructive dialogs.** The `danger` action is the primary on the right and the safer alternative (such as "Archive instead") is the `default` secondary on the left, split `50/50`.
7. **No Cancel in footers.** The header `×` dismisses, so footers carry real actions ("Discard" and "Save", never "Cancel"). "Cancel" appears only in popups (which have no `×`): `compact`, `subtle`, right-aligned with the action.
8. **Steps.** "Back" and "Next" split `50/50` across the footer.

## Best practices

### Size the Modal to its content with a step of `MODAL_WIDTHS`.

A short confirmation takes `6-col`, a short form `8-col`, a table or an editor
`10-col`. A step grows with the screen; a fixed number keeps one size on every
screen.

<DoDontPair
    doExample={<div style={scaledScreen}><Modal show renderAs="inline" width="6-col" title="Remove this session?" body="The student is told it was canceled." secondaryButton={{ text: 'Keep session' }} primaryButton={{ text: 'Remove', appearance: 'danger' }} onClose={() => {}} /></div>}
    doCaption="The narrowest step for a short question."
    dontExample={<div style={scaledScreen}><Modal show renderAs="inline" width="10-col" title="Remove this session?" body="The student is told it was canceled." secondaryButton={{ text: 'Keep session' }} primaryButton={{ text: 'Remove', appearance: 'danger' }} onClose={() => {}} /></div>}
    dontCaption="The widest step around one sentence."

### Keep Close on a Modal unless the person has to answer it.

An informational Modal keeps its close button; `showCloseButton={false}` is for
a decision that has to be answered from the footer.

<DoDontPair
    doExample={<div style={narrowScreen}><Modal show renderAs="inline" title="Session details" description="Monday, 4:00 PM" body="Lincoln Middle with Jordan, 45 minutes." primaryButton={{ text: 'Done' }} onClose={() => {}} /></div>}
    doCaption="Close stays on an informational dialog."
    dontExample={<div style={narrowScreen}><Modal show renderAs="inline" showCloseButton={false} title="Session details" description="Monday, 4:00 PM" body="Lincoln Middle with Jordan, 45 minutes." primaryButton={{ text: 'Done' }} onClose={() => {}} /></div>}
    dontCaption="No way out of an informational dialog."
/>

### Add `dividers` when the Modal body scrolls.

The rules mark where the header and footer stay put while the body scrolls; a
short body reads cleaner without them.

<DoDontPair
    doExample={<div style={shortCap}><Modal show renderAs="inline" dividers title="Session notes" body={longBody} primaryButton={{ text: 'Done' }} onClose={() => {}} /></div>}
    doCaption="Dividers around a scrolling body."
    dontExample={<div style={shortCap}><Modal show renderAs="inline" dividers title="Session notes" body="One short note." primaryButton={{ text: 'Done' }} onClose={() => {}} /></div>}
    dontCaption="Dividers around a short body."
/>

### Give the Modal footer a button.

`showBottomButtons` defaults to true, and the footer renders only when
`primaryButton`, `secondaryButton` or `footer` is given; describe the actions as
objects and the component renders the `FooterActions` pair.

### Show a follow-up decision in the same Modal; a Modal never opens on another Modal.

The confirm view swaps the same Modal's title, body and footer, and Back returns
to the form with what was typed. A Modal raised from an open Modal stays closed
and calls its `onClose`; a confirm Modal may open over a Panel, a Popup or a
focused task, each with its own Blanket.

```jsx
<Modal
  title={confirming ? 'Discard changes?' : 'Session settings'}
  show={open}
  onClose={close}
  secondaryButton={confirming ? { text: 'Back', onClick: () => setConfirming(false) } : { text: 'Discard', onClick: close }}
  primaryButton={confirming ? { text: 'Discard changes', appearance: 'danger', onClick: discard } : { text: 'Save', onClick: save }}
>
  {confirming ? 'Your edits to this session are not saved.' : settingsForm}
</Modal>
```

## Accessibility

- **Escape and a press on the Blanket close the Modal by default.** `keyboard`
  and `blanket` both default to `true`. Turning either off leaves the close
  button as the exit, so keep that button. The header, and its close button, is
  left out only when the Modal has no `title`, no `description`, no
  `headerActions` and `showBottomButtons` is false.
- **The close button is labeled `Close`**, hard-coded. Its icon is
  `aria-hidden`. `showCloseButton={false}` removes it; keep Escape or a footer
  action as a way out.
- **The title is the dialog's h1 and its accessible name**, through
  `aria-labelledby`: the dialog reads as its own page. The `description`
  describes it, through `aria-describedby`. A Modal with no title takes
  `ariaLabel`.
- **A body that scrolls is focusable.** Once the content runs past the cap, the
  body gets `tabIndex={0}` so a keyboard user can scroll it.
- **Loading is announced as busy.** `loading` sets `aria-busy` on the body while
  the skeleton bars stand in for it.
- **Opening traps focus inside the dialog and closing returns it to the
  trigger.** Tab cycles within the dialog; a view change (the confirm view
  swapping in) moves focus into the dialog again.
- **Turn off the Blanket click for an inline confirmation of a destructive
  action.** Set `blanket="static"` (or `false`) while the confirmation shows,
  so a stray click outside cannot destroy something by accident; Close, Escape
  or the footer's Back still work.
- **Focus order is Close, then the content, then the secondary action, then
  the primary action.**
- **`renderAs="inline"` is for docs previews only.** It draws the panel with no
  Blanket, no focus trap and no Escape, so a live dialog keeps the default
  `renderAs="modal"`.
