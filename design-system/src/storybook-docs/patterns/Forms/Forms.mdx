## The kinds of form

There is no Form component or template. A form is a `Fieldset` of fields inside a host, and the host owns the title and the footer. Pick the kind by the task; its host page has the layout, the footer and the sizes.

## Usage

Use Forms when a page asks for input that is saved together: adding a student, logging a session, a reflection, profile settings. Ask only what is needed, group fields under a `Fieldset` legend of two or three words, keep one column except for pairs that belong together (first and last name, date and time), and reveal a conditional field under the answer that needs it rather than adding a separate one.

## Alternatives

- For one value on a record page, use `InlineEdit`; it saves on its own.
- For settings that apply at once, group `SettingRow` items under section headings on the page; a `Toggle` never waits for Save.
- For a filter, follow <a target="_top" href="./?path=/docs/patterns-filtering--docs">Filtering</a>: filters are not a form.
- For a decision with no fields, use <a target="_top" href="./?path=/docs/templates-modal--docs">Modal</a> · Active.

## Best practices

### Validate a field when it loses focus and clear the error once the rule is met.

<RuleTag kind="automatic" />

The error shows on the field, says what to fix, and goes away as soon as the value passes. Nothing is checked while typing. A warning accepts the value; a field is invalid only when the form cannot go on.

### Keep the submit button enabled and let it show what is missing.

<RuleTag kind="automatic" />

A disabled submit gives no direction and leaves the tab order. Pressing it marks every missing field and moves focus to the first; the body scrolls to it. The button disables only while sending, when it swaps its label for a spinner in place and keeps its width.

### Keep a blocked submit in the same Modal.

<RuleTag kind="automatic" />

Mark the field, say what to fix inline, scroll the body to it, and shake once <PlannedTag />. Never a second dialog for the error. Reduced motion drops the shake; the color, icon, message and focus move carry it. A server failure: <a target="_top" href="./?path=/docs/patterns-states-errors--docs">Errors</a>.

<DoDontPair
    doExample={<ErrorOnField />}
    doCode={CODE.ErrorOnField}
    doCaption="The message under the field, in the same Modal."
    dontExample={<ErrorInSecondDialog />}
    dontCode={CODE.ErrorInSecondDialog}
    dontCaption="A second dialog over the first, with the field left unexplained."
/>

### Mark only the minority case in the label, in plain text.

<RuleTag kind="review" />

When most fields are required, mark the optional ones `"(optional)"` (`labelMarker="optional"`). When most fields are optional, mark the required ones `"(required)"` (`labelMarker="required"`). The marker is plain text in the label's type style, in `--ds-text-subtle`, never a symbol or legend. Required controls still set `isRequired`, so screen readers get `aria-required` and the visible `"(required)"` is hidden from them to avoid saying it twice. Choice flows (`RadioGroup` and `CheckboxGroup` across onboarding, quizzes, check-ins, and surveys) apply the same minority rule to selection controls: the majority selection type uses `appearance="soft"` (selected fill, border, and trailing check with no radio dot or checkbox box), while the minority selection type keeps its visible control (`card` or `plain`) so people notice when a question switches between single-select and multi-select.

<DoDontPair
    doExample={<MinorityMarked />}
    doCaption="Two required fields stay unmarked; only the optional field says so."
    dontExample={<MajorityMarked />}
    dontCaption="Every field carries a marker, so none stands out."
/>

### Put help in the caption, never in a tooltip.

<RuleTag kind="automatic" />

A caption stays after the person types and is read by a screen reader with the field. A tooltip never carries the only copy of anything. An explanation most people will never need opens from an `InlineMessage` beside the field.

<DoDontPair
    doExample={<HelpInCaptionCase />}
    doCaption="Help in the caption, where it stays after typing."
    dontExample={<HelpInTooltipCase />}
    dontCaption="Help only in a tooltip: gone on touch, gone after typing."
/>

### Ask before leaving with unsaved edits.

<RuleTag kind="automatic" />

Close, Discard, Cancel (on a page form) and navigating away raise a 4-col Modal: Back returns without losing anything typed; Discard is Danger. A form already in a Modal asks in that Modal's confirm view, so two layers never become three. A form with no edits leaves at once. In a multi-step task, Back in the inner sidebar asks first if anything is unsaved.

### Prefer a bound input to a free one.

<RuleTag kind="review" />

Up to five choices: `RadioGroup` or checkboxes, visible at once. Six or more: `Select`. A date: `DatePicker`. A number: min and max. A radio group starts unanswered and never falls back to its first option. A `Toggle` applies at once, so anything that waits for Save is a `Checkbox`.

### Give the form a title from its host and a legend for each group.

<RuleTag kind="review" />

The form's title is the page, Panel or Modal heading, never a generic "Form". Groups take a `Fieldset` legend, two or three words, a noun phrase. Labels are sentence case, one to three words, naming the field rather than what to do.

### Keep a form to one column.

<RuleTag kind="review" />

Pair two fields side by side only when they belong together, such as first and last name, or date and time. Anything else reads down one column.

<DoDontPair
    doExample={<OneColumnFields />}
    doCaption="One column, so the eye moves straight down."
    dontExample={<TwoColumnFields />}
    dontCaption="Unrelated fields scattered across two columns."
/>

### Keep a short edit beside the page.

<RuleTag kind="review" />

Editing a row opens a Panel so the person keeps the page in view. A Modal is for a rare, critical task with fewer than five fields.

<DoDontPair
    stacked="Each figure is a page with a table and a Panel beside it, too wide to halve."
    doExample={<EditInPanel />}
    doCode={CODE.EditInPanel}
    doCaption="A short edit in a Panel, the rows still in view."
    dontExample={<EditInModal />}
    dontCode={CODE.EditInModal}
    dontCaption="The same short edit in a Modal that covers the rows."
/>

### Set autofill on every field the browser can fill.

<RuleTag kind="automatic" />

`autoComplete` on name, email, phone and address fields. Prefill what is already known, such as the student picked from a row.

## Accessibility

- Every input has a visible label. A group is a `fieldset` with a `legend`; its one error is announced once.
- A field error is announced and sets `aria-invalid`; the submit moves focus to the first invalid field. A server message is announced when it appears.
- A required field sets `aria-required` whether or not it carries a visible `"(required)"` marker; only the form's minority case is marked in the label text.
- A sending button keeps its name and sets `aria-busy`; the secondary action stays reachable.
- A dialog opens only from a person's action. Focus goes to the first input and stays trapped until it closes.
