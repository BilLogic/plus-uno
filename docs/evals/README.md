# evals/ — the quality loop (L4)

Criteria, tests, fixtures, results — one folder, one loop.

| Dir | Holds | Rule |
|---|---|---|
| `rubrics/` | what "good" means, one rubric per artifact type (PRD, prototype, share-out, lesson, skill, agent-spec, bot-answer D1–D9) | YAML criteria + prose rationale; applied by `reviewers/rubric-applier` |
| `scenarios/` | `<skill>.md` — ≥3 scenarios (query + expected behavior) per skill | **written BEFORE the skill body** (evals-first); baseline without the skill, then write the minimal skill that passes |
| `fixtures/` | frozen golden inputs + answer keys per skill (see fixtures/README.md) | benchmarks run against these — a moving fixture measures nothing |
| `runs/` | `*.jsonl` — one line per scored run, plus `apply-log.jsonl` (one row per executed Flow-5 verdict: target · verdict link · timestamp) | interim store until the Notion Eval Runs DB exists; written at flow exits |

**Where a uno-bot eval run lands.** `run-evals.mjs` writes `eval-results.json` to the repo root — every case's verdict, its `passedRuns/samples` tally, its deterministic failures, the judge's reason, the subject the board handed it, and the full transcript of every turn. `.github/workflows/uno-bot-evals.yml` uploads that file as the `eval-results` artifact on every run, pass or fail, so a red blocker can be read rather than re-run. Each turn's `tools` list carries every call the model made with the arguments it sent, and — since 2026-09-05 with #452 — what each RESULT said about itself: `note`, `visibility`, `error`, and nothing else. Never rows, never message or blueprint content: an artifact is a file that outlives the run, and results in it would be the S2 disclosure failure moved into the instrument. The three fields are what a search-shaped failure is diagnosed from — S3 read 0/3 against r254 with all three replies saying workspace search "isn't available on this turn", and the artifact could not say which leg produced it. Nothing is written to `runs/` by this suite; that directory is the skill flows' store.

**How a turn is run is a dependency (#511).** `run-evals.mjs` takes a TURN TRANSPORT — `{ runTurn({ prompt, history, pending, surface }), fetchSubject?(need, case) }` — and `--transport=worker` is the default, so the cron's plain `node agents/uno-bot/scripts/run-evals.mjs` means what it always meant: a POST to the deployed Worker's `/debug/eval` route, now `workerTransport` in `agents/uno-bot/scripts/eval-transport.mjs`. `WORKER_URL` and `DEBUG_TOKEN` are required by that transport, not by the runner. The summary records which transport answered, because scores produced in-process and scores produced against a deployment are different measurements and nothing else in the file tells them apart. Everything the runner does between the turns — the fixture walk, the subject substitution, the deterministic checks, the history threading, the sampling arithmetic — is transport-agnostic and is exercised by `agents/uno-bot/scripts/run-evals.test.mjs`, which replays real fixture cases (R3, C1, B2) through a fake transport under `node --test`; the in-process adapter that calls the Worker's Turn module directly is `--transport=local`, below. **The judge's rubric has one home**: it is loaded from `rubrics/bot-answer.md` and its `dimensions:` block is quoted into the judge prompt verbatim (`eval-rubric.mjs`), so a dimension added or sharpened reaches the next run with no second edit — `eval-rubric.test.mjs` fails when a D-id in the document does not reach the prompt. The condensed paraphrase the runner used to carry is gone.

**`--transport=local` runs the suite in-process, from recorded replies (#512).** `agents/uno-bot/scripts/eval-transport-local.mjs` calls the same `evalTurnRequest → runTurn → evalTurnResponse` path the Worker's route takes, with the same in-memory ThreadState seeded from the runner's history and the same recording Delivery — so no deployment, no `WORKER_URL`, no `DEBUG_TOKEN` and no model spend. The model is a **recording**: `fixtures/recordings/<case>.json` holds that case's model replies (and, where a case turns on one, what each lookup returned), replayed through the real agent loop behind the fake `ModelProvider`, so the loop's own rules — a side-effect call staged as a gated proposal, `proposal_resolve` authorized against the pending card — all run against a fixed draw. `fixtures/recordings/README.md` is the format; **`source: "authored"` vs `"captured"` is load-bearing** and reaches the results file's `build` field. Three cases are recorded today and both facts matter: **R3, R5 and R11, all AUTHORED by hand** — writing #512 needed no Vertex credential, and a fabricated score is worse than a missing one. So a local run measures **the turn** (the dispositions, the gate's idempotency, the cancel bounce, the history write) and measures **nothing about the model**; the Monday cron keeps `--transport=worker`, which is the run that does. `scripts/eval-record.mjs` captures the rest off a live `/debug/eval` when someone has credentials (`--case=ID`… or `--all`) — **and nobody needs to hold those credentials locally (#544)**: `.github/workflows/uno-bot-evals.yml` takes a `mode` input, so `gh workflow run uno-bot-evals.yml -f mode=record` records all 34 cases from CI, where `WORKER_URL` and `DEBUG_TOKEN` already live, and `gh run download <id> -n eval-recordings` fetches what it wrote — to be read, then committed into `fixtures/recordings/` in its own PR. It is a dispatch and not a cron because a capture is 34 live billable model runs; `mode: run` (the default, and the Monday cron) is unchanged. A case that declares a run-time `subject` is captured **with its row** (#541): the Worker's subject read answers first, the row fills the case's placeholders, and it is written into the recording as `subject`, so the local transport replays the case against the board it was recorded on — a recording without one skips by name, as a missing recording does. A case with no recording **SKIPS** — `transport.unsupported(case)` names the reason, the runner counts it apart exactly as it counts an unsatisfiable subject condition (#415), and it never fails a blocker: a gate that is red for "no recording" is a gate that gets switched off. The local job runs on every pull request in `.github/workflows/check-harness.yml`.

**The eval route is an ADAPTER over Turn (#499).** `/debug/eval` no longer runs a pipeline of its own. The 127-line driver that called `runAgent` directly — and mirrored production's clarify gate by calling `preflight` beside it, and stopped there — is deleted; the route builds a `TurnRequest` from the case body and hands it to the same `runTurn` a Slack message takes (`agents/uno-bot/src/eval/turn-adapter.ts`, with the pure request/response halves in `eval/turn-case.ts`). So an eval turn now passes through preflight, the confidence pre-check, the absence check, the draft judge, the gate's idempotency rules and the history write exactly as a designer's turn does — every guard that lives above the loop was previously invisible to the suite. Two dependencies differ from production and only two: **Delivery records instead of posting** (`recordingDelivery` — no 👀, no thinking line, no card in a real conversation), and a **resolution is recorded instead of executed** (the old driver never executed one either; a suite that files a Notion card per sample is a suite nobody can run three times). Thread state is in-memory, seeded with the history the runner sent, so the store-backed rules — the "(Cancelled the proposed …)" bounce, the compaction trigger — read the conversation production would. `agents/uno-bot/tests/eval-adapter.test.ts` holds the parity: the same text as an eval case and as a Slack message produces the same `TurnOutcome`, the same Delivery calls and the same stored history.

**The response shape is unchanged**, because the runner and this document are its contract: `ok` · `error` · `build` · `ms` · `result` · `dials` · `tools` · `references` · `gateAsk` · `narration` · `subrequests` · `subrequest_hosts` · `internal_subrequests` · `budget_trips`. Two now mean something sharper. `result.text` on an answered turn is the body that was **delivered** — after the confidence pre-check and the judge — where the old route reported the model's raw draft, so a `textRegex` assertion scored prose no designer would have read. And an `asked` turn reports the gated proposal plus `gateAsk` where the clarify gate asked (the pair `allowProposalIfGateAsk` reads, R8/R12), but reports the **text** where nothing was gated and nothing staged — the deterministic cancel bounce, which R5's turn 3 asserts as `expectKind: ["text"]`. One field is added: `turn` — the disposition, the tier, the route, the judge's verdict and whether a card was staged. Nothing reads it yet; it is the half the old driver could not report at all.

**⚠️ RE-BASELINE PENDING — the fixtures have NOT been re-scored against the adapter.** `fixtures/uno-bot-cases.json` is unchanged by #499. Re-running it needs Vertex credentials and a deployed Worker, neither of which exists outside Actions, and a fabricated score is worse than a missing one. **The re-baseline is the next scheduled run** — the Monday 08:00 UTC cron of `.github/workflows/uno-bot-evals.yml`, or a `workflow_dispatch` of it against a deployment carrying #499 — and it is the FIRST run whose scores measure the production pipeline, so a case that moves has most likely moved because a guard it never met is now in front of it (the judge scoring a judged body, the gate bouncing a re-card). Whoever reads that run records the before/after in the run history: the last pre-#499 run's per-case verdicts against the first post-#499 run's, in `runs/` with the build ids of both. Until that line exists, treat the current fixture expectations as the pre-adapter baseline.

The summary at the top of the file records **what was measured, and what measured it**: `workerBuild` — the `build` the `/debug/eval` route reported, i.e. the deployment that actually answered — and `fixture` — the checkout revision plus a hash of the fixture bytes as loaded. Both, because neither is inferable from the other: Actions checks out at depth 1 so a per-file `git log` is empty, and a locally-edited fixture is not the committed one. `passed` / `failed` / `skipped` are three counts, not two — a case whose run-time condition nothing on the board satisfied is skipped, and folding it into either of the others would describe a run that did not happen (#415).
