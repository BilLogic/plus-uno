<FoundationSection title="Overview">

WCAG 2.1 AA is the minimum bar for every PLUS screen. Tutors use PLUS on laptops during live sessions, often while sharing their screen with a student, so a screen stays legible at any zoom level and works under assistive technology.

These are the accessibility rules every PLUS screen meets. Most of them are built into the tokens and the patterns, so a screen built from them meets the rules by default. Each component page adds the rules for its own name, role and keyboard behavior. Each foundation page owns the rules for its own subject: contrast in Color, heading order in Typography, the focus ring in Border and Radius, reduced motion in Motion.

</FoundationSection>

<FoundationSection title="Heading levels">

**A heading's tag is its place in the outline. Its style is its look.** Choose
the two separately. A heading that has to look small but sits high in the
page's outline is an `h2` set in a small style, never an `h4` picked for its
size.

- The tag comes from where the heading sits in its own page: one level below
  the heading it belongs to, never skipping a level.
- The style comes from **Typography**: `--heading-medium` for a section,
  `--heading-xsmall` for a card title, and so on.
- A component that can land at different depths, such as a card, takes its
  heading level from where it sits.
- Text that only looks like a heading, such as a metric, is not a heading. Set
  it in its style on a paragraph, so it takes no place in the outline.
- Removing a heading can create a skip: `h2, h3, h4` with the `h3` taken out
  becomes `h2` → `h4`. Read the outline before you remove or re-tag one.

**For developers.** A heading's look comes from its text style, not its tag:
`<h2 className="heading-large">` draws the same at any level, and so does a
rule that sets `font: var(--heading-large)`. Re-tag a heading for the outline
and keep its style, and select it by its class, not its tag.

In the docs, the `.sbdocs hN` rules apply to MDX prose only: each is fenced
with `:not(:where(.docs-story *))`, so a story's own headings draw at their
real size. A new rule of that kind needs the same fence.

</FoundationSection>

<FoundationSection title="The top of the outline">

**Every page's outline starts with an `h1`.** The rule above places a heading
within the outline; this one says the outline has a top.

- A page with a visible title marks that title up as the `h1`.
- A page whose name sits only in the topbar still has an `h1`, hidden
  visually but kept for assistive technology.
- A visually hidden heading is moved off-screen, never hidden with
  `display: none`, which would remove it for screen readers too.
- A modal's title is the dialog's own `h1`.
- A fragment is not a page. A card or a label never carries an `h1`.

Adding the `h1` moves everything under it: a page that ran `h4 → h4` becomes
`h2 → h3`, with the look unchanged.

**For developers.** axe's `heading-order` rule cannot see a missing top, because the first heading
has no predecessor, and its `page-has-heading-one` rule does not run when the
check is scoped to a story. `PageLayout` renders a page's hidden `h1` from
its `title`.

</FoundationSection>

<FoundationSection title="Contrast">

Text clears 4.5:1 and icons, borders and the focus ring clear 3:1 against what
they sit on, in light and dark. Under increased contrast the bars are 7:1 and
4.5:1. Each text and icon token is made for a surface or a fill, and using the
pair keeps the contrast, so it is never checked one component at a time.

<Canvas of={AccessibilityStories.ContrastPairings} sourceState="none" />

Never put a neutral text token on a bold fill, or an inverse token on a
surface. **Color** shows every pair, measured, in both modes.

</FoundationSection>

<FoundationSection title="Focus">

Focus is shown by the **focus ring**, never by a fill.

- The ring is 2px of `--ds-border-focused`, drawn 2px outside a control's
  edge, at the control's radius + 2. Inside a row or a tab, it is drawn inset.
- The control's fill stays as it is, and its opacity stays at 100%.
- The ring clears 3:1 against what it sits on, so every interactive element,
  including cards, table rows and list items, has the same visible indicator.

See Do and don't for the ring beside the fill-only mistake.

<FoundationSubsection title="Focus in overlays">

Opening a `Modal` or a `PatternDrawer` moves focus inside it and keeps Tab
there; closing it returns focus to the control that opened it. Both do this
themselves, and a new overlay gets the same behavior by building on Base UI.

</FoundationSubsection>

</FoundationSection>

<FoundationSection title="Keyboard">

Every interactive element can be reached and operated from the keyboard.

- Tab order follows the visual reading order: left to right, top to bottom.
- A widget follows its keyboard pattern: arrow keys move through a menu, and
  Escape closes a `Modal`.
- New interactive behavior (open and closed state, focus, keyboard) is built
  on Base UI (`@base-ui/react`), which supplies these patterns.

</FoundationSection>

<FoundationSection title="Screen readers">

- Reach for the semantic element first (`button`, `nav`, `main`, `table`),
  and for ARIA only when no element fits.
- A control with no visible text is named with `aria-label` or
  `aria-labelledby`.
- Content that changes without a page load is announced through a live
  region (`role="status"` with `aria-live="polite"`), as the `Table` bulk-action
  count is.

</FoundationSection>

<FoundationSection title="Disabled">

A disabled component is dimmed as a whole to `--ds-opacity-disabled` (0.4),
rather than recoloring its parts. Disabled elements are not focus targets, and
they keep their label, so people can still tell what is unavailable.

</FoundationSection>

<FoundationSection title="Forms">

- Every field has a visible label tied to its control. A field that renders
  its own label wires the label's `htmlFor` to the control's `id` itself;
  `Select` and `DatePicker` render none, so the form supplies it.
- An error says what went wrong and how to fix it, on the field, through its
  `errorMessage`.
- A required field takes `required`, which draws the asterisk, and the form
  puts one line above its first field: "Required fields are marked with an
  asterisk (*)."
- Related fields are grouped in a `Fieldset`, which renders a `fieldset` and
  its `legend`.

</FoundationSection>

<FoundationSection title="Charts">

Every chart describes itself to screen readers: its type, its axes, each
series and each point, and its data can be read with the keyboard. A chart is
a labeled group inside its section, not a landmark of its own, so a dashboard
of six charts does not add six entries to the landmark menu. Give every chart
a title or a label, and never carry a series by color alone.

**For developers.** The charts share `chartTheme`, which turns on the Highcharts accessibility
module and sets `landmarkVerbosity: 'disabled'`. A chart that builds its own
options carries `accessibility: chartTheme.accessibility` itself. Never wrap a
chart in `aria-hidden` to quiet a labeling warning: that hides the keyboard
proxies the module creates.

</FoundationSection>

<FoundationSection title="Automated checks">

Every story runs axe in the Storybook test suite, and a story may not add a
violation, so a component that breaks a rule here is caught before it ships.

**For developers.** Run the checks for a set of stories with:

```bash
npx vitest --project=storybook --run <path>
```

</FoundationSection>
